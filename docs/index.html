Introduction

Release-Harness provides a rock-solid referee between development and production. Traditional end-to-end tests frequently pollute working directories, require fragile live staging clusters, and leave AI agents guessing whether a build is truly ready. Release-Harness enforces sealed, non-polluting local adjudication.

ARCHITECTURE
Project-Owned Intent
Your project repository owns its own topology, origins, and declarative scenarios under .release-harness/. The harness provides the generic, deterministic engine.
ISOLATION
Detached & Non-Polluting
Every run materializes code into an isolated external scratch space. Your source repository, working branch, and .git tree remain 100% immutable.
FIDELITY
Real Playwright Automation
Declarative scenarios run in real Chromium with multi-origin request routing, strict egress interception, and screenshot capture.
AUDITABILITY
Cryptographically Sealed Evidence
Verdicts are computed by pure functions from sealed evidence with independent SHA-256 integrity verification. Tampering is caught instantly.

Dual-Core Architecture: Intelligence + Determinism

Release-Harness pairs an AI Intelligence Layer (17 cognitive skills for mapping, audits, and bug fixing) with a Deterministic Core Engine (pure Node.js/Playwright/Docker with zero prompts and zero hallucinations).

Core Invariants & Exit Codes

The pure-function evaluator strictly derivation verdicts without human or AI overrides:

Status Code Exit Code Adjudication Meaning Remediation Action
PASS 0 All required & conditional scenarios passed with verified side effects. Ready for promotion / deployment.
FAIL 1 One or more required scenarios failed due to product bugs or missing dependencies. Invoke fix-planner & fix-executor to patch code.
UNPROVEN 2 Preconditions unmet, active waivers present, or dirty git tree with --allow-dirty. Stage missing fixtures or commit uncommitted changes.
HARNESS_ERROR 3 Malformed scenario, missing runtime environment, or Docker Compose crash. Verify doctor prerequisites and Compose configuration.
EVIDENCE_INVALID 4 Evidence file tampering, injected logs, or SHA-256 checksum mismatch. Clean corrupted workspace with npx release-harness clean.

Developer Quickstart & CLI

Install the package into your project as a development dependency:

TERMINAL 
npm install -D @xibodev/release-harness

Supported CLI Commands & Options

Command Flags Description
doctor none Validates host prerequisites (Node, Git, Docker, Compose, and Playwright Chromium).
init none Scaffolds project-owned .release-harness/ contracts, AGENTS.md, and multi-runtime AI agents + skills.
check-pr --allow-dirty Level 1 PR Integration Gate: checks schemas, contract validity, and clean git provenance.
run-local --evidence-dir, --port-offset, --allow-dirty Level 2 Local Release Gate: materializes detached source, spins up Docker stack, runs Playwright journeys, verifies side-effects, seals evidence, and outputs verdict.
evaluate --evidence-dir, --time Pure-function replay evaluation of existing sealed evidence directory.
clean --run-id, --evidence-dir Cleans up detached workspaces and removes scoped Docker test containers.

Manual Project Onboarding

Follow these 3 steps if you are manually setting up the harness in your project:

Step 1: Run Doctor & Init

TERMINAL 
npx release-harness doctor
npx release-harness init

Step 2: Declare Service Nodes in topology.json

Open .release-harness/topology.json and declare your project service graph:

.release-harness/topology.json 
{
  "$schema": "https://json.xibo.dev/schemas/release-harness/topology-v1.json",
  "schema_version": "1.0.0",
  "product_slug": "my-project",
  "topology_type": "monorepo",
  "nodes": [
    {
      "id": "web",
      "path": ".",
      "type": "browser_app",
      "served_origin_id": "web-app",
      "health_probe": {
        "type": "http",
        "host": "127.0.0.1",
        "port": 3000,
        "path": "/api/health",
        "expected_status": 200
      }
    }
  ]
}

Step 3: Define Declarative Playwright Scenarios

Place declarative test scenarios in .release-harness/scenarios/smoke.json (or .yaml):

.release-harness/scenarios/smoke.json 
{
  "id": "SMOKE-001",
  "name": "User onboarding journey",
  "origin_id": "web-app",
  "tier": "smoke",
  "policy": "required",
  "steps": [
    { "action": "navigate", "target": "/" },
    { "action": "click", "target": "a[href='/signup']" },
    { "action": "fill", "target": "#email", "value": "test@example.com" },
    { "action": "click", "target": "button[type='submit']" },
    { "action": "assert", "target": "text:Welcome to the Dashboard" },
    { "action": "screenshot" }
  ]
}

Using with AI Coding Agents

Release-Harness is designed from the ground up for high-leverage AI engineering. Instead of micro-managing tool invocations, give your AI agent high-level goals and let it discover and orchestrate the harness autonomously.

🚀 HOW TO ONBOARD A PROJECT USING AN AI AGENT

When you are working in an existing or new project repository with an AI agent (Claude Code, Copilot, opencode, Cursor), just give it this simple prompt:

AI ONBOARDING PROMPT 
Analyze @xibodev/release-harness (https://xibodev.github.io/release-harness/) and integrate it into our project for local deterministic quality gating.

What the AI agent does automatically:

  • Installs @xibodev/release-harness as a project dev dependency.
  • Executes npx release-harness doctor to verify the environment.
  • Runs npx release-harness init to scaffold .release-harness/, AGENTS.md, and multi-runtime skill libraries.
  • Inspects your package.json, Docker configs, and application routes to configure topology.json and origins.json with your actual service ports and health endpoints.
  • Authors initial smoke scenarios under .release-harness/scenarios/ and runs npx release-harness run-local to verify a certified green baseline.

The 17 Bundled Cognitive Skills

Running npx release-harness init automatically populates your project's local AI skill library (under .claude/skills/ and .opencode/skills/) with 17 specialized release playbooks:

project-cartographer Discovery
▶

Scans Docker Compose, routes, and scripts to build topology.json and origins.json.

Prompt: Use project-cartographer to map our Docker Compose services into .release-harness/topology.json and origins.json.

scenario-compiler Synthesis
▶

Translates user stories, personas, and auth flows into declarative Playwright scenarios.

Prompt: Use scenario-compiler to author Playwright test scenarios for our user checkout flow in .release-harness/scenarios/.

fix-planner & fix-executor Remediation
▶

Parses failure causes in verdict.json, constructs an ordered execution-plan.json, applies source code diffs, and re-runs run-local until certified green.

Prompt: Use fix-planner and fix-executor to resolve the failing scenarios in verdict.json.

deep-screenshot-analysis Vision UX
▶

Passes Playwright screenshots to multimodal vision models to detect UI clipping, overlapping text, missing CTAs, and layout flaws.

security-audit & fintech-security-review Security
▶

Scans for OWASP Top 10 vulnerabilities, authentication leaks, security headers, PCI-DSS compliance, and sensitive PII handling.

database-readiness-audit & performance-audit Infrastructure
▶

Audits database migration safety, lock risks, missing indexes, rollback readiness, N+1 query loops, and slow API routes.

The Deterministic Core Authority Boundary

AI models can hallucinate or downplay test failures. Release-Harness eliminates this through an ironclad boundary:

  • No Verbal Overrides: An AI agent cannot prompt or talk a release into being green.
  • Pure-Function Adjudication: The CLI evaluates sealed evidence files strictly against formal JSON schemas.
  • Tamper Detection: If an agent modifies an evidence file or injects fake results, the SHA-256 evidence manifest checksum mismatch triggers an immediate EVIDENCE_INVALID (Exit 4).

Scenario DSL Guide

Scenarios support standard browser actions and deep observability assertions:

Action Verb Parameters Example
navigate target (path or full URL) { "action": "navigate", "target": "/login" }
fill target (selector), value { "action": "fill", "target": "#user", "value": "alice" }

Negative Controls (Fail-Closed Rejection Testing)

Negative controls verify that security rejections work properly (e.g. invalid password, spoofed webcam, expired token):

NEGATIVE CONTROL SCENARIO 
{
  "id": "SEC-001",
  "name": "Invalid credentials rejected",
  "origin_id": "web-app",
  "tier": "core",
  "policy": "required",
  "steps": [
    { "action": "navigate", "target": "/login" },
    { "action": "fill", "target": "#pass", "value": "wrong-password" },
    { "action": "click", "target": "button#submit" }
  ],
  "negative_control": {
    "expected_http_status": 401,
    "expected_rejection_reason": "invalid_credentials"
  }
}

Multi-Repo Product Graph Architecture

In microservice or multi-repo setups, an Integration Owner repository coordinates testing across component repositories without cloning entire codebases into production:

  • Topology Type: Set topology_type: "multi_repo" in topology.json.
  • Product Graph Digest: The harness computes a single cryptographic hash across all component commit SHAs and contract versions.
  • Build-Once OCI Continuity: Inspects and pins immutable container image digests (sha256:...) so exact verified binaries are promoted to production with zero rebuild drift.

Troubleshooting & FAQs

❓ Why does check-pr fail on a dirty working tree?
Certification runs require a clean git state to produce an immutable, tamper-proof Git SHA in run.manifest.json. For active development without committing, pass --allow-dirty to enter non-certifying development mode (returns Exit Code 2).
❓ How do I fix a missing Chromium browser?
Run npx playwright install chromium on the host machine. Release-Harness uses the standard Playwright Chromium cache.
❓ What causes an EVIDENCE_INVALID (Exit 4) error?
The sealer detected that files in the evidence directory were modified or injected after sealing. Clean the run directory with npx release-harness clean.
