Deterministic Quality Gates & Local UAT for Software Products

A portable, non-polluting test harness and release adjudication engine. Consumable by human developers and autonomous AI coding agents as a standard npm dependency.

Install via npm 
npm install -D @xibodev/release-harness

Introduction

Release-Harness bridges the gap between unit tests and production deployments. While traditional E2E tests often leak state, depend on fragile external staging environments, and pollute working directories, Release-Harness enforces sealed, deterministic local adjudication.

🎯 Product-Owned Intent
Your repository defines its own topology, origins, and test scenarios under .release-harness/. The harness provides the generic, deterministic execution engine.
🛡️ Detached & Non-Polluting
Every test run materializes code into an isolated external scratch space. Your source repository, working branch, and .git remain strictly untouched.
⚡ Real Playwright Automation
Declarative JSON/YAML scenarios are executed in Chromium with request routing, egress policy filtering, and screenshot capture.
🔒 Sealed Evidence & Signatures
Verdicts are computed by pure functions from sealed evidence with independent SHA-256 integrity verification. Tampering or incomplete evidence is caught immediately.

Core Invariants

  • Deterministic Adjudication: PASS (Exit 0), FAIL (Exit 1), UNPROVEN (Exit 2), HARNESS_ERROR (Exit 3), EVIDENCE_INVALID (Exit 4).
  • Zero Repository Mutation: Execution must never write into or mutate the source repository or .git/.
  • Sealed Network Execution: Outbound requests to undeclared external endpoints are blocked by default.
  • Independent Side-Effect Proof: S3/MinIO bucket uploads, database rows, and Redis state are probed out-of-band.

Installation & CLI

Install the public facade package in your product repository:

Terminal 
npm install -D @xibodev/release-harness

CLI Commands

Command Purpose
npx release-harness doctor Validates host prerequisites (Node, Git, Docker, Compose, Playwright/Chromium).
npx release-harness init Scaffolds a clean product-owned .release-harness/ contract directory.
npx release-harness check-pr Level 1 PR Integration Gate: checks contracts, schema validity, and clean git provenance.
npx release-harness run-local Level 2 Local Release Gate: materializes detached source, spins up Docker stack, runs Playwright journeys, verifies side-effects, seals evidence, and outputs verdict.
npx release-harness clean Cleans up detached workspaces and removes scoped test containers.

Onboarding a Product Repository

Follow these 3 steps to onboard any existing or new software repository:

Step 1: Run Doctor & Init

Terminal 
npx release-harness doctor
npx release-harness init

Step 2: Customize Served Origins & Topology

Open .release-harness/topology.json and declare your service nodes (e.g. Next.js web frontend, FastAPI backend, PostgreSQL database):

.release-harness/topology.json 
{
  "$schema": "https://json.xibo.dev/schemas/release-harness/topology-v1.json",
  "schema_version": "1.0.0",
  "product_slug": "my-saas-app",
  "topology_type": "monorepo",
  "nodes": [
    {
      "id": "web",
      "path": ".",
      "type": "browser_app",
      "served_origin_id": "web-app",
      "health_probe": {
        "type": "http",
        "host": "127.0.0.1",
        "port": 3000,
        "path": "/api/health",
        "expected_status": 200
      }
    }
  ]
}

Step 3: Define Declarative Playwright Scenarios

Place declarative test scenarios in .release-harness/scenarios/smoke.json (or .yaml):

.release-harness/scenarios/smoke.json 
{
  "id": "SMOKE-001",
  "name": "User onboarding journey",
  "origin_id": "web-app",
  "tier": "smoke",
  "policy": "required",
  "steps": [
    { "action": "navigate", "target": "/" },
    { "action": "click", "target": "a[href='/signup']" },
    { "action": "fill", "target": "#email", "value": "test@example.com" },
    { "action": "click", "target": "button[type='submit']" },
    { "action": "assert", "target": "text:Welcome to the Dashboard" },
    { "action": "screenshot" }
  ]
}

Using with AI Coding Agents

Release-Harness is designed from the ground up to be orchestrated by AI agents (Claude Code, GitHub Copilot CLI, opencode, Cursor, Codex).

🤖 The Autonomous Verification Loop

You tell the AI agent what to build or fix. The agent writes the code, then invokes npx release-harness run-local. The deterministic harness acts as the referee—the agent reads the structured failure causes in verdict.json and iterates autonomously until achieving a certified PASS (Exit 0).

Agent Prompting Recipes

Prompt Recipe for Claude Code:

Prompt 
I want to implement the user registration feature. 
Use @release-conductor or follow this loop:
1. Run `npx release-harness check-pr` to ensure our contracts are valid.
2. Implement the feature in frontend and backend.
3. Run `npx release-harness run-local --evidence-dir .quality-run/evidence`.
4. Read `verdict.json` and fix any failing scenarios or unmet preconditions.
5. Loop until you get a certified PASS (exit code 0). Do not declare done until exit code is 0.

Prompt Recipe for GitHub Copilot CLI:

Prompt 
copilot: Run the deterministic quality gate:
npx release-harness run-local
If verdict.json has failed scenarios or exit code != 0, inspect the screenshot evidence in the evidence directory, resolve the defects in code, and re-run until exit code 0.

Prompt Recipe for opencode:

Prompt 
Run the release-conductor workflow on our current branch:
1. Validate contracts: `npx release-harness check-pr`
2. Execute local UAT: `npx release-harness run-local`
3. If exit code is 1 or 2, use fix-planner and fix-executor to resolve defects.
4. Clean up workspaces when done with `npx release-harness clean`.

Prompt Recipe for Cursor / Codex:

Prompt 
Please execute `npx release-harness run-local` in the terminal to verify the changes against the product-owned scenarios in `.release-harness/scenarios/`.
Inspect the generated `verdict.json` summary. If there are failures, fix the root cause and re-run until the verdict is PASS.

The Deterministic Core Authority Boundary

AI agents are prone to hallucinating "everything looks good" or dismissing test failures as minor. Release-Harness eliminates this through an unbreakable boundary:

  • Sole Verdict Authority: Only the deterministic CLI engine derives verdicts from cryptographically sealed evidence.
  • No Verbal Overrides: An AI agent cannot prompt or talk a release into being green.
  • Tamper Proof: If an agent modifies an evidence file or injects fake results, the SHA-256 evidence manifest divergence triggers an immediate EVIDENCE_INVALID (Exit 4).

Scenario DSL Guide

Scenarios support standard browser actions and deep observability assertions:

Action Verb Parameters Example
navigate target (path or full URL) { "action": "navigate", "target": "/login" }
fill target (selector), value { "action": "fill", "target": "#user", "value": "alice" }
click target (selector) { "action": "click", "target": "button.submit" }
assert target (text:..., url:..., or selector) { "action": "assert", "target": "text:Success" }
screenshot none { "action": "screenshot" }

Negative Controls (Fail-Closed Rejection Testing)

Negative controls verify that security rejections work properly (e.g. invalid password, spoofed webcam, expired token):

Negative Control Scenario 
{
  "id": "SEC-001",
  "name": "Invalid credentials rejected",
  "origin_id": "web-app",
  "tier": "core",
  "policy": "required",
  "steps": [
    { "action": "navigate", "target": "/login" },
    { "action": "fill", "target": "#pass", "value": "wrong-password" },
    { "action": "click", "target": "button#submit" }
  ],
  "negative_control": {
    "expected_http_status": 401,
    "expected_rejection_reason": "invalid_credentials"
  }
}

Independent Side-Effect Probes

Verify that expected out-of-band state changes actually occurred in storage, database, or queues:

Side-Effect Verification 
{
  "id": "DOC-UPLOAD-01",
  "name": "ID Document Uploaded to Storage",
  "origin_id": "web-app",
  "tier": "core",
  "steps": [
    { "action": "navigate", "target": "/upload" },
    { "action": "upload", "target": "input[type='file']", "value": "fixtures/passport.jpg" }
  ],
  "expected_side_effects": [
    {
      "service": "minio",
      "probe_type": "s3_object_exists",
      "params": {
        "host": "127.0.0.1",
        "port": 9000,
        "bucket": "kyc-documents",
        "key_prefix": "passport.jpg"
      }
    }
  ]
}
