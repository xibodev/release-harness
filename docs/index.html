Introduction

Release-Harness provides a rock-solid referee between development and production. Traditional end-to-end tests frequently pollute working directories, require fragile live staging clusters, and leave AI agents guessing whether a build is truly ready. Release-Harness enforces sealed, non-polluting local adjudication.

ARCHITECTURE
Project-Owned Intent
Your project repository owns its own topology, origins, and declarative scenarios under .release-harness/. The harness provides the generic, deterministic engine.
ISOLATION
Detached & Non-Polluting
Every run materializes code into an isolated external scratch space. Your source repository, working branch, and .git tree remain 100% immutable.
FIDELITY
Real Playwright Automation
Declarative scenarios run in real Chromium with multi-origin request routing, strict egress interception, and screenshot capture.
AUDITABILITY
Cryptographically Sealed Evidence
Verdicts are computed by pure functions from sealed evidence with independent SHA-256 integrity verification. Tampering is caught instantly.

Core Invariants

Status Code Exit Code Adjudication Meaning
PASS 0 All required and conditional scenarios passed with verified side-effects. Certified for release.
FAIL 1 One or more required scenarios failed due to product defects or unmet required dependencies.
UNPROVEN 2 Preconditions unmet or active waivers present (e.g. non-certifying local development mode).
HARNESS_ERROR 3 Malformed scenario, environment missing, or Docker Compose startup failure.
EVIDENCE_INVALID 4 Evidence file tampering, missing artifacts, or SHA-256 checksum divergence detected.

Developer Quickstart & CLI

Install the package into your project as a development dependency:

TERMINAL 
npm install -D @xibodev/release-harness

Supported CLI Commands

Command Description
npx release-harness doctor Validates host prerequisites (Node, Git, Docker, Compose, and Playwright Chromium).
npx release-harness init Scaffolds a clean project-owned .release-harness/ contract directory.
npx release-harness check-pr Level 1 PR Integration Gate: checks schemas, contract validity, and clean git provenance.
npx release-harness run-local Level 2 Local Release Gate: materializes detached source, spins up Docker stack, runs Playwright journeys, verifies side-effects, seals evidence, and outputs verdict.
npx release-harness clean Cleans up detached workspaces and removes scoped test containers.

Onboarding an Existing Project

Follow these 3 steps to onboard any software project from scratch:

Step 1: Run Doctor & Init

TERMINAL 
npx release-harness doctor
npx release-harness init

Step 2: Declare Service Nodes in topology.json

Open .release-harness/topology.json and declare your project service graph:

.release-harness/topology.json 
{
  "$schema": "https://json.xibo.dev/schemas/release-harness/topology-v1.json",
  "schema_version": "1.0.0",
  "product_slug": "my-project",
  "topology_type": "monorepo",
  "nodes": [
    {
      "id": "web",
      "path": ".",
      "type": "browser_app",
      "served_origin_id": "web-app",
      "health_probe": {
        "type": "http",
        "host": "127.0.0.1",
        "port": 3000,
        "path": "/api/health",
        "expected_status": 200
      }
    }
  ]
}

Step 3: Define Declarative Playwright Scenarios

Place declarative test scenarios in .release-harness/scenarios/smoke.json (or .yaml):

.release-harness/scenarios/smoke.json 
{
  "id": "SMOKE-001",
  "name": "User onboarding journey",
  "origin_id": "web-app",
  "tier": "smoke",
  "policy": "required",
  "steps": [
    { "action": "navigate", "target": "/" },
    { "action": "click", "target": "a[href='/signup']" },
    { "action": "fill", "target": "#email", "value": "test@example.com" },
    { "action": "click", "target": "button[type='submit']" },
    { "action": "assert", "target": "text:Welcome to the Dashboard" },
    { "action": "screenshot" }
  ]
}

Using with AI Coding Agents

Release-Harness is purpose-built to act as an impartial referee for AI coding agents (Claude Code, GitHub Copilot CLI, opencode, Cursor, Codex).

💡 HOW TO ONBOARD AN EXISTING PROJECT USING AN AI AGENT

If you are already in your project repository working with an AI agent, copy and paste the onboarding prompt below. The AI agent will install the package, initialize contracts, and map your services automatically:

ONBOARDING PROMPT FOR AI AGENT 
We are onboarding this project to @xibodev/release-harness for deterministic quality gating.
Please follow these steps:
1. Install the tool: `npm install -D @xibodev/release-harness`
2. Check prerequisites: `npx release-harness doctor`
3. Initialize the contract scaffolding: `npx release-harness init`
4. Inspect our docker-compose and package scripts to configure `.release-harness/topology.json` and `.release-harness/origins.json` with our real service ports and health endpoints.
5. Create an initial smoke scenario in `.release-harness/scenarios/smoke.json` covering our landing and login pages.
6. Verify Level 1: `npx release-harness check-pr`
7. Run the local gate: `npx release-harness run-local` and confirm exit code 0.

The Deterministic Core Authority Boundary

AI models can hallucinate or downplay test failures. Release-Harness eliminates this through an ironclad boundary:

  • No Verbal Overrides: An AI agent cannot prompt or talk a release into being green.
  • Pure-Function Adjudication: The CLI evaluates sealed evidence files strictly against formal JSON schemas.
  • Tamper Detection: If an agent modifies an evidence file or injects fake results, the SHA-256 evidence manifest checksum mismatch triggers an immediate EVIDENCE_INVALID (Exit 4).

Scenario DSL Guide

Scenarios support standard browser actions and deep observability assertions:

Action Verb Parameters Example
navigate target (path or full URL) { "action": "navigate", "target": "/login" }
fill target (selector), value { "action": "fill", "target": "#user", "value": "alice" }
click target (selector) { "action": "click", "target": "button.submit" }
assert target (text:..., url:..., or selector) { "action": "assert", "target": "text:Success" }
screenshot none { "action": "screenshot" }

Negative Controls (Fail-Closed Rejection Testing)

Negative controls verify that security rejections work properly (e.g. invalid password, spoofed webcam, expired token):

NEGATIVE CONTROL SCENARIO 
{
  "id": "SEC-001",
  "name": "Invalid credentials rejected",
  "origin_id": "web-app",
  "tier": "core",
  "policy": "required",
  "steps": [
    { "action": "navigate", "target": "/login" },
    { "action": "fill", "target": "#pass", "value": "wrong-password" },
    { "action": "click", "target": "button#submit" }
  ],
  "negative_control": {
    "expected_http_status": 401,
    "expected_rejection_reason": "invalid_credentials"
  }
}

Independent Side-Effect Probes

Verify that expected out-of-band state changes actually occurred in storage, database, or queues:

SIDE-EFFECT PROBE SPECIFICATION 
{
  "id": "DOC-UPLOAD-01",
  "name": "ID Document Uploaded to Storage",
  "origin_id": "web-app",
  "tier": "core",
  "steps": [
    { "action": "navigate", "target": "/upload" },
    { "action": "upload", "target": "input[type='file']", "value": "fixtures/passport.jpg" }
  ],
  "expected_side_effects": [
    {
      "service": "minio",
      "probe_type": "s3_object_exists",
      "params": {
        "host": "127.0.0.1",
        "port": 9000,
        "bucket": "kyc-documents",
        "key_prefix": "passport.jpg"
      }
    }
  ]
}
