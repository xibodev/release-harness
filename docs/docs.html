Introduction

Release-Harness provides a rock-solid referee between development and production. Traditional end-to-end tests frequently pollute working directories, require fragile live staging clusters, and leave AI agents guessing whether a build is truly ready. Release-Harness enforces sealed, non-polluting local adjudication.

ARCHITECTURE
Project-Owned Intent
Your project repository owns its own topology, origins, and declarative scenarios under .release-harness/. The harness provides the generic, deterministic engine.
ISOLATION
Detached & Non-Polluting
Every run materializes code into an isolated external scratch space. Your source repository, working branch, and .git tree remain 100% immutable.
FIDELITY
Real Playwright Automation
Declarative scenarios run in real Chromium with multi-origin request routing, strict egress interception, and screenshot capture.
AUDITABILITY
Cryptographically Sealed Evidence
Verdicts are computed by pure functions from sealed evidence with independent SHA-256 integrity verification. Tampering is caught instantly.

Dual-Core Architecture: Intelligence + Determinism

Release-Harness pairs an AI Intelligence Layer (18 cognitive skills for mapping, audits, and bug fixing) with a Deterministic Core Engine (pure Node.js/Playwright/Docker with zero prompts and zero hallucinations).

Core Invariants & Exit Codes

The pure-function evaluator strictly derivation verdicts without human or AI overrides:

Status Code Exit Code Adjudication Meaning Remediation Action
PASS 0 All required & conditional scenarios passed with verified side effects. Ready for promotion / deployment.
FAIL 1 A required result failed, or certification stopped before writing a verdict. Inspect verdict causes when present; otherwise follow runtime diagnostics.
UNPROVEN 2 Preconditions unmet, active waivers present, or dirty git tree with --allow-dirty. Inspect underlying results and resolve failures before committing.
HARNESS_ERROR 3 Malformed scenario, missing runtime environment, or Docker Compose crash. Follow runtime diagnostics; do not infer a product defect from exit 3 alone.
EVIDENCE_INVALID 4 Evidence file tampering, injected logs, or SHA-256 checksum mismatch. Clean corrupted workspace with npx release-harness clean.

Developer Quickstart & CLI

UPGRADING FROM 1.1.0 — READ FIRST

v1.2.0 corrects behaviour that was previously wrong. A run that was green on 1.1.0 may legitimately fail on 1.2.0. Each of these is a correction, not a regression:

  • Git-ignored files no longer reach the workspace. Certification runs also exclude untracked files; --allow-dirty development runs include untracked files that are not ignored. If a build depends on a missing .env or local fixture, inspect git status, git check-ignore, and materialization warnings. Commit non-secret assets or provide configuration through your Compose environment; never commit local credentials.
  • sql_query scenarios now exit 3. The probe never executed any SQL; the previous green was unearned. Use a custom probe.
  • Harness faults report exit 3 where they previously reported exit 1 as a product failure. Check any CI that assumed exit 1 meant your code was broken.
  • --allow-dirty no longer masks integrity failures. It still yields exit 2 for a would-be pass or fail, but a harness error keeps exit 3 and invalid evidence keeps exit 4.
  • Scaffolded skills are namespaced release-harness-* so they cannot shadow same-named skills you already have. Unnamespaced copies from 1.1.0 are left in place; remove them manually if unwanted.
  • Contracts are validated against their schemas at load time, so an unsupported service or probe_type is rejected with a clear message instead of surfacing deep in the engine.

Supported CLI Commands & Options

Command Flags Description
doctor none Validates host prerequisites (Node, Git, Docker, Compose, and Playwright Chromium).
init --with-agents, --contracts-only, --force, --dry-run Scaffolds project-owned .release-harness/ contracts. A bare init writes contracts only; --with-agents adds AGENTS.md, AI-ADOPTION.md and the multi-runtime agent and skill bundle. Unknown flags are rejected with exit 3.
skills list, info <skill-name> Inspects all packaged cognitive skills, capabilities, target directories, and scaffold status without extracting templates. info accepts bare or release-harness- prefixed names.
check-pr --allow-dirty Level 1 PR Integration Gate: checks schemas, contract validity, and clean git provenance.
run-local --evidence-dir, --port-offset, --allow-dirty Level 2 Local Release Gate: materializes detached source, spins up Docker stack, runs Playwright journeys, verifies side-effects, seals evidence, and outputs verdict.
evaluate --evidence-dir, --time Pure-function replay evaluation of existing sealed evidence directory.
clean --run-id, --evidence-dir Cleans up detached workspaces and removes scoped Docker test containers.

Artifact-First Project Onboarding

Do not start from blank schemas. Let the bundled skills derive contracts from source, then review and approve the generated artifacts:

Step 1: Run Doctor & Scaffold the Skill Bundle

TERMINAL

npx release-harness init --with-agents

Step 2: Derive and Review Service Contracts

Invoke release-harness-project-cartographer to inspect Compose services, real ports, routes, and health probes. Review its generated topology.json and origins.json diff. The shape below is a reference, not a blank form to author by hand:

  "schema_version": "1.0.0",
  "product_slug": "my-project",
  "topology_type": "monorepo",
  "nodes": [
    {
      "id": "web",
      "path": ".",
      "type": "browser_app",
      "served_origin_id": "web-app",
      "health_probe": {
        "type": "http",
        "host": "127.0.0.1",
        "port": 3000,
        "path": "/api/health",
        "expected_status": 200
      }
    }
  ]
}

Using with AI Coding Agents

AI-ADOPTION.md is the standard integration protocol for AI coding agents. init --with-agents scaffolds it alongside the cognitive skills so every runtime follows the same artifact-first sequence and exit-code rules.

🚀 HOW TO ONBOARD A PROJECT USING AN AI AGENT

When you are working in an existing or new project repository with an AI agent (Claude Code, Copilot, opencode, Cursor), just give it this simple prompt:

AI ONBOARDING PROMPT 
Analyze @xibodev/release-harness (https://xibodev.github.io/release-harness/) and integrate it into our project for local deterministic quality gating. Run `npx release-harness skills list` to inspect the packaged bundle, then `npx release-harness init --with-agents` and read AI-ADOPTION.md. Use `release-harness-project-cartographer` and `release-harness-scenario-compiler` to derive contract artifacts from source, and present their diffs for review instead of hand-authoring JSON.

Golden Sequence after installing the package:

  1. Run npx release-harness doctor to verify Docker, Compose, Playwright, and other prerequisites.
  2. Run npx release-harness init --with-agents to scaffold contracts, AI-ADOPTION.md, and the skill bundle. Restart or reload the active agent session so it reindexes new skills. Use npx release-harness skills list to inspect the bundle before or after scaffolding.
  3. Invoke release-harness-project-cartographer to derive topology.json and origins.json from source, then present the generated diff for human review.
  4. Invoke release-harness-scenario-compiler to compile scenarios and side-effect probes from user stories and personas, then present the generated diff for human review.
  5. While generated changes are uncommitted, run npx release-harness run-local --allow-dirty and inspect underlying results (exit 2 is expected). Resolve failures, approve and commit the artifacts, then run npx release-harness run-local for a certified GREEN exit 0.
  6. Run npx release-harness check-pr on pull requests and npx release-harness run-local on release branches.

The Deterministic Core Authority Boundary

AI models can hallucinate or downplay test failures. Release-Harness eliminates this through an ironclad boundary:

  • No Verbal Overrides: An AI agent cannot prompt or talk a release into being green.
  • Pure-Function Adjudication: The CLI evaluates sealed evidence files strictly against formal JSON schemas.
  • Tamper Detection: If an agent modifies an evidence file or injects fake results, the SHA-256 evidence manifest checksum mismatch triggers an immediate EVIDENCE_INVALID (Exit 4).

Scenario DSL Guide

Scenarios support standard browser actions and deep observability assertions:

Action Verb Parameters Example
navigate target (path or full URL) { "action": "navigate", "target": "/login" }
fill target (selector), value { "action": "fill", "target": "#user", "value": "alice" }
click target (selector) { "action": "click", "target": "button.submit" }
assert target (text:..., url:..., or selector) { "action": "assert", "target": "text:Success" }
screenshot none { "action": "screenshot" }

Custom Probes — Asserting on Your Actual Deliverable

The named probes cover services the harness speaks: minio/s3, redis, and mailpit. But a product whose deliverable is a file — a rendered video, a compiled binary, a generated PDF, an exported dataset — needs to assert on the artifact itself. A gate that drives your UI and certifies green while saying nothing about the file you shipped is not certifying the thing that matters.

A custom probe runs a command your project owns:

{
  "expected_side_effects": [
    {
      "service": "custom",
      "probe_type": "custom",
      "params": {
        "command": "./scripts/probe-artifact.sh",
        "args": ["renders/final.mp4"],
        "expect_exit_code": 0
      }
    }
  ]
}

The harness executes the command against the materialized workspace, treats the exit code as the verdict, and seals stdout and stderr into evidence/probes/ where they are hashed with the rest of the run's evidence. It holds no opinion about what you assert — the core never learns what ffmpeg is.

  • Commit the script. The command must live in your repository and be named in the committed contract. A command generated at run time would let the thing being certified author its own assertion.
  • Exit 0 means the assertion held. Any other code fails the scenario as a product failure. Write diagnostics to stderr — they are captured as evidence.
  • Assert the deliverable, not the mechanism. Check that the .mp4 is valid H.264 of the expected duration, not that a tool was invoked.
  • Keep it deterministic and offline. No network, no wall-clock dependence, no machine-specific state.
  • Exit code only. There is no expect_stdout_contains; assert inside your script and signal through the exit code.
⚠ sql_query is not implemented. The harness ships no SQL client, so it cannot execute a query or evaluate expected_rows_count / forbidden_values. As of v1.2.0 it fails closed and says so, rather than reporting success whenever the database port happened to be open. Assert database state with a custom probe that runs your own query tool.

Existing Playwright Test Suite Adapter

Mature projects with existing TypeScript Playwright suites do not need to rewrite tests into JSON. Release-Harness includes a first-class adapter:

Adapter Execution Flow 
// Programmatic or CLI integration
import { PlaywrightSuiteAdapter } from '@xibodev/release-harness-core/playwright-adapter';

const adapter = new PlaywrightSuiteAdapter({
  workingDir: './e2e',
  configPath: 'playwright.config.ts',
  expectedTestIds: ['auth-login', 'billing-checkout'],
});

const result = await adapter.executeSuite();
// Ingests native JSON reporter, extracts test IDs, durations, attachments, traces, and normalizes into raw-results.json
  • Native Execution: Executes npx playwright test --reporter=json directly.
  • Inventory & Skip Enforcement: Validates that expected test IDs were discovered and flags unexpected skips on required tests as PRODUCT_BUG.
  • Evidence Binding: Automatically extracts screenshot attachments and trace zip files into the sealed evidence directory.

Multi-Repo Product Graph Architecture

In microservice or multi-repo setups, an Integration Owner repository coordinates testing across component repositories without cloning entire codebases into production:

  • Topology Type: Set topology_type: "multi_repo" in topology.json.
  • Product Graph Digest: The harness computes a single cryptographic hash across all component commit SHAs and contract versions.
  • Build-Once OCI Continuity: Inspects and pins immutable container image digests (sha256:...) so exact verified binaries are promoted to production with zero rebuild drift.

Level 1 (PR Gate) and Level 2 (Local Release UAT Gate) are fully implemented and proven in v1.2.0. Levels 3 and 4 are currently design-only specifications and are intentionally disabled in the CLI until their full acceptance suites pass.

LEVEL 3 (ROADMAP v1.2)
run-ephemeral
Deploys the exact frozen product lock to an ephemeral PR preview environment with production-equivalent TLS and proxy routing, executes full-product scenarios, archives sealed evidence, and proves environment destruction.
LEVEL 4 (ROADMAP v1.3)
verify-canary
Runs narrow, reversible synthetic canary assertions in production to verify deployed release digests, health telemetry, and webhook side-effects before completing deployment promotion.

Troubleshooting & FAQs

❓ Why does check-pr fail on a dirty working tree?
Certification runs require a clean git state to produce an immutable, tamper-proof Git SHA in run.manifest.json. For active development without committing, pass --allow-dirty to enter non-certifying development mode (returns Exit Code 2).
❓ How do I fix a missing Chromium browser?
Run npx playwright install chromium on the host machine. Release-Harness uses the standard Playwright Chromium cache.
❓ What causes an EVIDENCE_INVALID (Exit 4) error?
The sealer detected that files in the evidence directory were modified or injected after sealing. Clean the run directory with npx release-harness clean.
