Deliberate propositions. Deterministic evidence.

Release-Harness gives human and agent authors one contract model and gives automation a deterministic adjudicator that cannot be talked into green.

Introduction

Agents and people author the same contract artifacts under the frozen model subject + assertions + requires + execution bindings. The deterministic core decides from accepted identity and sealed evidence.

AUTHORING
Evidence before acceptance
Drafts remain mutable and may be incomplete. Claims distinguish observed facts, bounded absence, source-asserted absence, inference, and what is not established.
IDENTITY
Content-addressed contracts
Acceptance freezes the proposition. Changing an assertion or normative reference creates a different digest; changing a local binding does not.
EXECUTION
HTTP and CLI
The beta supports deterministic status/body checks and direct command exit/stdout/stderr checks with independently captured streams.
CHAIN OF CUSTODY
Sealed and verifiable
Evidence is sealed before adjudication. Verification checks the contract, evidence, verdict, and links between them.

Getting started

The short lifecycle is:

init â†’ draft â†’ inspect / resolve questions â†’ validate â†’ accept â†’ bind â†’ run â†’ verify
  1. Initialize: release-harness init installs the protocol and empty authoring directories. It asserts nothing about the project.
  2. Draft: run release-harness draft new example-tool, inspect the project, and edit the draft plus record. A draft may be valid but incomplete.
  3. Validate: release-harness validate checks schema and semantics. release-harness draft status example-tool lists unresolved blockers.
  4. Accept: release-harness accept --draft example-tool --by "release owner" records responsibility and freezes identity. It is not proof.
  5. Bind and run: bind each symbolic target to a URL or direct executable, then run the accepted contract. Only an eligible accepted contract can certify.
  6. Verify: release-harness verify checks chain of custody after the run.
AGENT-ASSISTED ADOPTION

An agent follows the same installed .release-harness/protocol/ADOPTION.md, authors the same artifacts, and encounters the same acceptance blockers. It cannot override adjudication or answer operator questions on its own.

One honest CLI example

This fictional command is deliberately generic:

// example-tool.js
const name = process.argv[2] ?? 'world';
console.log(`hello, ${name}`);

The evidence record cites what was actually inspected:

{
  "id": "prints-greeting",
  "claim": "example-tool.js prints a greeting and exits 0",
  "status": "observed",
  "evidence": { "source": "example-tool.js:1-2" }
}

The draft asserts only what that evidence supports:

{
  "id": "A1",
  "kind": "cli",
  "target": "tool",
  "description": "the CLI prints a greeting and exits cleanly",
  "expect": {
    "args": "Ada",
    "exit_code": 0,
    "stdout_contains": "hello, Ada"
  },
  "supported_by": ["prints-greeting"]
}
release-harness validate --draft example-tool
release-harness accept --draft example-tool --by "release owner"
release-harness bind local --target "tool=node example-tool.js"
release-harness run --binding local
release-harness verify

A PASS proves that accepted assertion held at that binding. It proves nothing else about the program.

Authoring and acceptance

The authoring plane keeps mutable drafts separate from immutable contracts. A claim has one of five statuses:

StatusMeaning
observedA cited source or completed probe directly establishes the claim.
observed_absentA bounded, completed search records its method, roots, exclusions, and completion.
asserted_absentA source or test explicitly says something must not exist.
inferredA reasoned conclusion, never silently upgraded to observation.
not_establishedThe available inspection cannot establish the proposition.

Blocking semantic questions remain open until evidence or an accountable operator resolves them. Acceptance records that responsibility and emits an immutable content-addressed contract. It does not say the software has passed.

Bindings, exploratory runs, and certification

Assertions name symbolic targets. A binding resolves those symbols for one environment:

release-harness bind local \
  --target "api=http://127.0.0.1:8080" \
  --target "tool=node example-tool.js"

Bindings are recorded in run identity but excluded from proposition identity. Direct CLI execution uses an executable plus argv with shell: false. Windows absolute paths, paths with spaces, POSIX paths, and PATH command names are supported; shell composition belongs in an explicitly reviewed wrapper script.

run --draft ... --exploratory provides authoring feedback but always remains UNPROVEN. A certifying run requires an accepted contract, complete bindings, and resolvable normative references before any assertion executes.

Normative references and multiple repositories

If another exact accepted contract changes what this subject's assertions mean, record its { ref, digest } under requires. That digest participates in contract identity. A package dependency or adjacent repository is not automatically normative.

Authors may inspect another repository when local evidence establishes relevance: a manifest dependency, workflow reference, generated schema source, deployment input, or explicit documentation pointer. If the relationship is real but no exact accepted digest can be established, leave the question unresolved. Do not invent a topology, repository role, or placeholder digest.

Trust boundary

  • Only a reached subject violating an accepted assertion may receive a PRODUCT finding.
  • Missing executables, missing file operands, unreachable endpoints, unresolved references, and harness faults retain non-product causes.
  • stderr may satisfy an author-written assertion, but unexpected stderr never determines attribution.
  • Evidence is sealed before adjudication; post-seal writes and broken chain links fail closed.
  • Neither a human explanation nor an AI recommendation can override the deterministic verdict.

Assertion vocabulary

Use release-harness draft kinds for the installed schema-derived vocabulary.

KindExpectation fieldsWhat it proves
httpmethod, path, status, body_containsA reached HTTP target returned the accepted deterministic status/body property.
cliargs, exit_code, stdout_contains, stderr_containsA directly launched executable returned the accepted exit/output property.

stdout and stderr stay separate. The vocabulary is intentionally small; additions require a demonstrated proposition, not a repository taxonomy.

CLI commands

CommandPurpose
doctorReport installed artifacts and whether anything is currently certifiable.

Exit codes

ExitMeaning
0Command succeeded; for a run, an eligible certifying run passed.
1An accepted assertion against a reached subject was violated.
2Nothing was proven: a valid draft may be blocked, or a run exploratory.
3Usage, contract, or binding problem; nothing ran.
4Harness, environment, or evidence-integrity failure.

Beta scope and limitations

BETA, NOT STABLE

Beta focuses on deterministic HTTP and CLI release assertions and on trustworthy contract authoring and adjudication. The assertion vocabulary will expand from demonstrated certification needs rather than repository taxonomy.

A PASS is scoped to the accepted assertions, exact normative references, source, and binding recorded for that run. It is not proof of complete coverage, security, production readiness, or authorization to deploy. Release-Harness directly executes trusted project commands and is not a sandbox.

Beta feedback

  • Trust/correctness: possible false certification, attribution, identity, evidence, or acceptance failure.
  • Expressiveness: an exact certification proposition cannot be written with current primitives.
  • Adoption: discovery, protocol, evidence, or semantic-question friction.
  • UX: messages and discoverability.
  • Compatibility: OS, runtime, package manager, shell, or filesystem behavior.

A proposed model expansion needs a concrete proposition, proof that subject + assertions + requires + execution bindings cannot represent it, and proof that an assertion primitive cannot solve it.
