    PRODUCT DOCUMENTATION

    From project contracts to a local gate.

    Define what your product must do. Run it in a detached workspace. Inspect a deterministic verdict backed by sealed evidence.

    Start manually → Use an AI agent

    What it does

    Release-Harness is an npm development dependency for project-owned quality gates. check-pr validates contracts and runs configured checks; run-local runs declarative browser scenarios and side-effect probes, then evaluates sealed evidence.

    Use it directly in a terminal or let an AI coding agent prepare contracts and run commands. AI assistance is optional. A local PASS proves the declared gate, not production readiness beyond that gate.

    Match the docs to your package

    This site describes the 2.0.0 release candidate (unreleased, not yet published). npm 1.2.0 remains the published release and does not include the changes called out below, including skills list/skills info and shared skill discovery. Released users should use the documentation at their installed version's Git tag. See versions & source usage.

    Install & manual quickstart

    No AI host is required. Start in your product's Git repository with npm and Git. Node.js 20 is the CI-tested baseline. The 2.0.0 candidate requires Node.js 20+; published 1.2.0 metadata declared Node.js 18+. Local Compose UAT also needs a running Docker Engine, Compose, and Playwright Chromium.

    INSTALL IN YOUR PRODUCT
    npm install -D @xibodev/release-harness@1.2.0 playwright
npx playwright install chromium
npx release-harness --version
npx release-harness doctor
npx release-harness init --contracts-only

    init writes contracts only, just like init --contracts-only. It does not discover your app, start services, or generate passing tests. Read doctor warnings even when it exits successfully.

    Configure your product

    1. Edit .release-harness/topology.json to describe your services and real HTTP or TCP health probes.
    2. Set origins.json URLs to your test services. Match each scenario's origin_id to an origin.
    3. Replace the generated smoke scenario with an assertion your application actually satisfies. Add independent probes for important side effects.
    4. Provide docker-compose.test.yml in the project root for an isolated test stack. The runner falls back to docker-compose.yml; review that file before running it. Without either file, it uses services you have already started.
    5. Review the contracts, then run a development baseline below. Commit non-secret contracts, fixtures, and dependency changes before clean certification.

    Existing files are preserved. init --force and init --overwrite reset contracts as well as agent files. They are not upgrade commands. Use init --dry-run to preview scaffolding.

    Use with an AI agent

    The same contracts and CLI apply. init --with-agents adds the release-conductor persona, AI-ADOPTION.md, and namespaced skill playbooks. Installing the npm dependency alone does not copy them into your project.

    OPTIONAL AGENT SCAFFOLDING
    npx release-harness init --with-agents

    Templates support Claude Code, GitHub Copilot, opencode, and shared agent instructions for Cursor/Codex. Use your host's documented agent selection and reload mechanism; disk files are not proof of host registration.

    Skill discovery Unreleased

    The current source contains 18 playbooks. Read-only discovery and the shared .agents/skills/ target are unreleased. With a source checkout installed as described under versions & upgrades, inspect:

    CURRENT SOURCE CLI, FROM YOUR PRODUCT DIRECTORY
    node /path/to/release-harness/packages/release-harness/bin/release-harness.js skills list
node /path/to/release-harness/packages/release-harness/bin/release-harness.js skills info project-cartographer

    info accepts bare or prefixed names. Invoke playbooks by their release-harness-* names. Reload the host if needed and verify its catalog; /init is not a portable reload command.

    Delegate work, review artifacts

    EXAMPLE PROMPT FOR A HOST WITH THE BUNDLE LOADED
    Use release-harness-project-cartographer to derive topology and origins from our services. Use release-harness-scenario-compiler to compile journeys with independent side-effect probes. Present the contract diff for review. Then use release-conductor to run the local gate with an external evidence root and report its verdict and causes. Propose targeted fixes before changing code; preserve unrelated working changes.

    Playbooks guide discovery, scenario design, audits, and remediation. They are not executable scanners or infrastructure installers. They need host file/shell tools; screenshot review also needs image input. Missing tools mean deferred checks, not passes.

    Authority boundary: AI review, risk scores, and verbal approval cannot replace the deterministic CLI result or weaken the contracts to make a run green.

    Development & certification

    Choose an evidence root outside your product repository. The following examples use a sibling directory. Run IDs must be unique: replace these example IDs for every new run; reusing one can mix or overwrite evidence.

    Example commands

    Run these commands from your configured product directory.

    DEVELOPMENT: UNCOMMITTED CHANGES ALLOWED
    npx release-harness run-local --allow-dirty --evidence-dir ../rh-evidence --run-id dev-001

    A dirty development run is non-certifying: a would-be pass or product failure becomes UNPROVEN (exit 2). Inspect the underlying failures. Harness and integrity faults still return exits 3 and 4. A clean tree is not made dirty merely by passing the flag.

    CERTIFICATION: CLEAN, REVIEWED SOURCE
    npx release-harness check-pr
npx release-harness run-local --evidence-dir ../rh-evidence --run-id release-001

    Ignored files do not reach the detached workspace. Nonignored untracked files are included only with --allow-dirty. Supply secrets through approved runtime configuration, never committed fixtures.

    CLI commands

    Run npx release-harness --help for the CLI you installed. Flags are command-specific.

    CommandPurpose & options
    doctorInspect host tools and discovered contracts. Takes no arguments; read warnings.
    initContracts by default. Options: --contracts-only or --with-agents (mutually exclusive), --dry-run, --force/--overwrite.
    skills list
    skills info <name>    		Unreleased. Inspect bundled playbooks and local scaffold files without writing. Does not query the host registry.
    check-prValidate contracts/provenance and run pr_gate.commands in the product working directory. Option: --allow-dirty. Dirty mode can return early before commands execute.
    run-localDetached local UAT. Options: --evidence-dir <root>, --run-id <id>, --port-offset <integer>, --allow-dirty, --time <ISO timestamp>.
    evaluateReplay sealed evidence. Requires --evidence-dir <run evidence directory>; use the original --run-id and --time for a repeatable comparison.
    cleanRemove a run's workspace and labelled containers. Supply both --run-id <id> and --evidence-dir <root> to keep cleanup scoped.

    --port-offset shifts browser and health/probe ports. It does not rewrite Compose port mappings: your test stack must publish the corresponding ports. The runner provides RUN_ID and PORT_OFFSET to Compose.

    Project contracts

    Keep contracts under .release-harness/. The CLI reads these standard paths; a schema field is not by itself a promise that every runtime consumes it. The JSON schemas define accepted shapes.

    Topology

    This example assumes a project-root application serving Welcome at http://127.0.0.1:3000/. Start it yourself or provide the Compose file described in the quickstart. Replace this assumption with your real application; these contracts do not implement a server.

    .release-harness/topology.json
    {
  "schema_version": "1.0.0",
  "product_slug": "my-project",
  "topology_type": "monorepo",
  "network_policy": { "mode": "sealed", "allowed_egress": [] },
  "nodes": [{
    "id": "web",
    "path": ".",
    "type": "browser_app",
    "served_origin_id": "web-app",
    "health_probe": {
      "type": "http", "host": "127.0.0.1", "port": 3000,
      "path": "/", "expected_status": 200
    }
  }]
}

    Origins

    An origin resolves to an HTTP(S) URL, either directly or through env:APP_URL (default http://127.0.0.1:3000). safe_for_live is a declaration, not authorization to test production.

    .release-harness/origins.json
    [{
  "origin_id": "web-app",
  "type": "browser_app",
  "auth": "none",
  "url_source": "http://127.0.0.1:3000",
  "route_families": ["/"],
  "safe_for_live": false,
  "evidence": ["package.json"]
}]

    Harness configuration

    Keep the generated schema_version, harness_version, and port_block. Set product_slug to match topology (my-project for the example). To enable PR checks, merge this fragment into harness.config.json, using scripts your product defines:

    CONFIG FRAGMENT: PRODUCT MUST DEFINE npm test
    {
  "pr_gate": {
    "commands": [{
      "id": "tests", "cmd": "npm test",
      "timeout_seconds": 120, "expected_exit_code": 0
    }]
  }
}

    check-pr does not infer lint or test scripts. Configure the commands you need. These commands execute in your checkout, not the detached UAT workspace.

    Scenarios & probes

    Each JSON or YAML scenario in .release-harness/scenarios/ declares an ID, origin, tier, policy, and browser steps. This smoke scenario matches the topology and origin above.

    .release-harness/scenarios/smoke.json
    {
  "id": "SMOKE-001",
  "name": "Landing page availability",
  "origin_id": "web-app",
  "tier": "smoke",
  "policy": "required",
  "steps": [
    { "action": "navigate", "target": "/" },
    { "action": "assert", "target": "text:Welcome" },
    { "action": "screenshot" }
  ]
}

    Supported actions: navigate, fill, click, select, check, upload, wait-for, assert, and screenshot. Assertions accept a selector, text:..., or url:.... Upload paths are passed directly to Playwright: relative paths resolve from the CLI working directory, not the detached workspace. Use reviewed nonsecret fixtures and do not assume upload contents are bound to detached-source provenance.

    Negative controls

    Prove an expected rejection, not just a successful happy path. Add the following fragment to a scenario whose steps submit invalid credentials to your app. Both the observed status and rejection reason must match.

    {
  "negative_control": {
    "expected_http_status": 401,
    "expected_rejection_reason": "invalid_credentials"
  }
}

    Independent side-effect probes

    Supported service probes cover MinIO/S3 object presence or absence, Redis keys/values, and Mailpit messages. Add expected_side_effects to the scenario that produces the effect. Seed isolated test services first; do not point these examples at customer data.

    SCENARIO FRAGMENT: LOCAL TEST OBJECT
    {
  "expected_side_effects": [{
    "service": "minio",
    "probe_type": "s3_object_exists",
    "params": {
      "host": "127.0.0.1", "port": 9000,
      "bucket": "test-documents", "key": "sample.txt"
    }
  }]
}

    The S3 probe uses key, not a prefix, and performs an HTTP object read without AWS request signing. Use an isolated readable test endpoint, not private production storage.

    Custom probes

    Use a reviewed project script to assert on a generated file or query test database state. This fragment assumes scripts/probe-artifact.mjs exists in your product and can access output/report.pdf from the detached workspace.

    SCENARIO FRAGMENT: PROJECT-OWNED ASSERTION
    {
  "expected_side_effects": [{
    "service": "custom",
    "probe_type": "custom",
    "params": {
      "command": "node",
      "args": ["scripts/probe-artifact.mjs", "output/report.pdf"],
      "expect_exit_code": 0,
      "timeoutMs": 60000
    }
  }]
}

    The command runs without shell interpolation, with the materialized workspace as its default working directory. Its numeric exit is compared with expect_exit_code (default 0); a mismatch is a product assertion failure. Invalid configuration, inability to start the command, timeouts, output overflow, and evidence-write failures are harness errors, not failed product assertions.

    Captured output is bounded and stored under evidence/probes/. Keep diagnostics free of secrets. Custom commands are trusted code, not sandboxed or made offline by the harness. There is no expect_stdout_contains; assert inside your script.

    sql_query is not implemented. It fails closed as a harness configuration error. Use a custom probe with your own query tool to verify database state.

    Playwright adapter

    PlaywrightSuiteAdapter is an exported programmatic adapter for existing suites. It executes Playwright's JSON reporter and returns normalized results. It is not wired into run-local and does not produce a sealed gate by itself.

    NODE.JS MODULE: RUN FROM YOUR PRODUCT ROOT
    import { PlaywrightSuiteAdapter } from
  '@xibodev/release-harness-core/playwright-adapter';

const adapter = new PlaywrightSuiteAdapter({
  workingDir: './e2e',
  configPath: './e2e/playwright.config.ts',
});
const result = await adapter.executeSuite();
console.log(result);

    Install the core package directly for programmatic use, along with your suite's Playwright dependencies. workingDir and configPath resolve from the calling process's directory. Supply expectedTestIds only using IDs confirmed in your JSON report.

    Attachment paths are returned in evidence_files; files are not copied or sealed. Your integration must collect attachments, bind the policy and expected inventory, seal evidence, and invoke evaluation. Skipped results are recorded, not automatically rejected as required-test failures by the adapter.

    CI usage

    Run check-pr on pull requests and local UAT on reviewed release changes. Pin dependencies with your lockfile. Use isolated runners with only test credentials: project scripts and Compose files execute code.

    This GitHub Actions example assumes committed contracts, a test Compose stack, playwright in dev dependencies, and configured pr_gate.commands. Separate PR and release jobs if their trust levels differ.

    EXAMPLE .github/workflows/quality.yml
    name: Quality gate
on: [push, pull_request]
permissions:
  contents: read
jobs:
  local-uat:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: npx release-harness check-pr
      - name: Run local UAT
        run: >-
          npx release-harness run-local
          --evidence-dir "${{ runner.temp }}/rh-evidence"
          --run-id "ci-${{ github.run_id }}-${{ github.run_attempt }}"
      - name: Retain evidence
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: release-evidence
          path: ${{ runner.temp }}/rh-evidence/runs
          retention-days: 7

    Keep evidence access restricted and choose retention deliberately. Screenshots, request data, and probe output may contain sensitive data. An early failure may leave no verdict or artifact; don't report a pass because an upload succeeded.

    Verdicts & evidence

    StatusExitMeaning & next action
    PASS0The declared gate passed. This is not a deployment command or proof of checks you did not declare.
    FAIL1A gate failed, or the CLI rejected the run before a verdict. Inspect causes and diagnostics.
    UNPROVEN2Unmet conditions, waivers, or dirty development. Resolve underlying failures before clean certification.
    HARNESS_ERROR3Configuration, environment, probe, or startup fault. UNKNOWN means unresolved attribution, not proof of a product bug.
    EVIDENCE_INVALID4Evidence failed integrity verification. Preserve the run; investigate before cleanup. Do not edit or reseal it to force a pass.

    For --evidence-dir ../rh-evidence --run-id release-001, inspect ../rh-evidence/runs/release-001/verdict.json, its sibling run.manifest.json, and sealed files in evidence/.

    REPLAY AN EXISTING RUN
    npx release-harness evaluate --evidence-dir ../rh-evidence/runs/release-001/evidence --run-id release-001

    For time-sensitive policy comparisons, add --time with the original evaluation timestamp. Unlike run-local, evaluate takes the evidence directory itself, not the output root. It prints a verdict; it does not rerun the application.

    Unreleased: startup observations are sealed when finalization succeeds, and replay preserves recorded network/harness faults. Arbitrary startup logs are omitted for secret safety. If no verdict was produced, report the diagnostic rather than inventing a result.

    SCOPED CLEANUP, AFTER EVIDENCE REVIEW
    npx release-harness clean --run-id release-001 --evidence-dir ../rh-evidence

    Omitting --run-id broadens container cleanup to other harness runs. Cleanup is not evidence repair.

    Architecture & security

    The public @xibodev/release-harness CLI delegates to @xibodev/release-harness-core. The core provides materialization, runners, probes, sealing, and evaluation; @xibodev/release-harness-schemas defines the contracts.

    1. Read project intent. Validate topology, origins, and scenarios.
    2. Materialize source. Copy eligible source into an external workspace and record provenance.
    3. Run local checks. Start the selected Compose stack, drive Chromium, and collect observations and probes.
    4. Seal and evaluate. Hash evidence and derive the verdict from recorded facts and policy.

    Multi-repository products & image records

    A multi_repo topology lets an integration-owner repository describe component repositories. The materializer resolves their source revisions and computes a product graph digest. Review the topology schema for repository fields.

    The local Compose runner records available OCI repository digests, with image-ID fallback. That is local provenance, not registry promotion, remote deployment verification, or a guarantee that production uses the same image.

    Trust boundaries

    • Trusted input: contracts, Compose files, PR commands, custom probes, and the execution host must be reviewed. Detached source is not a sandbox for hostile code.
    • Evidence integrity: hashes detect changes relative to the seal. They do not establish an independent signer or defend against an attacker controlling the collector and all evidence.
    • Network scope: browser egress filtering does not isolate containers, custom probes, build processes, or the host. Apply infrastructure controls separately.
    • Unreleased network hardening: topology policy is canonical; legacy config policy is accepted and conflicts are rejected. HTTPS/WSS checks tunnel destination host, port, and transport, not encrypted content, SNI, or certificate identity. Allowed relays remain outside this boundary. Non-proxied WebRTC UDP is suppressed without per-attempt verdict violations.
    • Private evidence: use synthetic data and restricted storage. Redaction is not a guarantee that every artifact is safe to publish.

    Read the security policy for reporting vulnerabilities and the supported security boundary.

    Contributing

    Contributions can improve scenarios, adapters, documentation, or the deterministic engine. Start with the contributor guide. Include a reproduction and a regression test for behavior changes; never replace a deterministic gate with an AI judgment.

    In a source checkout, install dependencies with npm ci and run npm test. The full gate includes schema, core, neutral-fixture, smoke, and fresh-install tests, and needs Docker, Chromium, tar, and OpenSSL. See the contributor guide for platform prerequisites and skipped coverage.

    Versions & upgrades

    Check npx release-harness --version and your lockfile before following examples. For a released package, browse the repository at its matching version tag. Source metadata reports 2.0.0, but this candidate is not yet published to npm; a source version string is not proof of publication.

    Breaking migration to 2.0.0 (unreleased)

    • Upgrade local Node, CI runners, and container images to Node.js 20+. The optional Playwright peer minimum is 1.50.0, matching core; install Chromium for the resolved version. The open-ended peer range does not certify untested future releases.
    • Sealed replay ignores caller-only overrides and uses manifest-covered facts. Rerun corrected contracts to change inputs; preserve old archives rather than editing or resealing them. Historical bundles missing required facts or containing linked evidence can be rejected.
    • Replace unsupported health probes with implemented HTTP or TCP probes. Probe configuration errors return exit 3, not silent success. Built-in SQL query assertions remain unsupported.
    • Use topology.json.network_policy as canonical. Remove conflicting legacy config policy and fix malformed fields. Config-only policy remains supported; missing policy remains open with a warning.
    • HTTPS/WSS filtering checks tunnel destinations, not encrypted content, TLS SNI, or certificate identity. Allowed relays and container-wide isolation are outside this boundary; suppressed WebRTC UDP attempts have no individual violation records.

    Try unreleased source

    Clone the repository separately from your product and run npm ci in that checkout. There is no compilation step for the JavaScript CLI. From your product directory, invoke that checkout's CLI instead of npx release-harness, replacing the path below. This uses source code, not the published npm package.

    node /path/to/release-harness/packages/release-harness/bin/release-harness.js --help

    Preserve project intent

    • Review the changelog and lockfile diff. Test upgraded gates before relying on their verdicts.
    • Keep existing contracts and host customizations. Repair individual files; do not blanket-run init --overwrite.
    • Update product_slug in topology and config together. Declare network policy explicitly rather than assuming absence means sealed.
    • Preserve old evidence. Stricter validation or missing historical facts may require a fresh run, not a modified archive.

    When moving from 1.1.0 to 1.2.0, account for ignored-file exclusion, fail-closed SQL probes, harness faults returning exit 3, integrity faults staying exit 4 in dirty mode, and namespaced skills. See release notes for detail.

    Troubleshooting

    Chromium is missing

    Install Playwright in the product and run npx playwright install chromium for that installation. On Linux CI, use --with-deps. A cache directory alone does not prove that the matching browser can launch.

    The smoke test fails after init

    The template expects Welcome at the configured origin. Replace it with your actual application assertion and verify the service URL, fixtures, and Compose health probe.

    A skill is on disk but absent from the host

    Reload or restart your AI host from the product repository, then inspect its catalog. Preserve your session context first. If reloading is unavailable, read the scaffolded SKILL.md directly and follow the procedure.

    A build file is missing in the workspace

    Inspect git status, git check-ignore, and materialization warnings. Keep non-secret required assets tracked; provide sensitive configuration at runtime.

    For other failures, start with the exit code and evidence. Preserve invalid evidence and use a new run ID after resolving the cause.
